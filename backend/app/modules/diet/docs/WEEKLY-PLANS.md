# 一周食谱、档案联动与执行反馈

本功能依赖只读公共目录和 006 引用缓存。它复用既有食谱评分、禁忌硬过滤、营养计算和成员 A 的账号授权；不产生实际摄入记录，不扣库存，不根据身高体重推算热量。

## 安装顺序与环境边界

迁移顺序为基础初始化 → 001 → 002 → 003 → 004 → **006 → 005**。编号不是部署顺序：005 使用 006 提供的公共/私人资源体系。001～004 的 SQL 和校验和保持不变；005、006 在独立 `diet_extension_schema_migrations` 登记，不写旧迁移登记表。普通 FastAPI 启动不会自动应用这两个扩展。

从 backend 目录使用 Python 3.12 虚拟环境，对已初始化的**独立临时测试库**显式执行：

```powershell
# $temporaryDatabase 必须是本次创建的临时 SQLite 库绝对路径。
# 不填默认 health.db，不复用旧演示库，不将本命令用于未经授权的正式数据。
& ..\.venv\Scripts\python.exe -B -m app.modules.diet.migration_006 --database $temporaryDatabase --apply
& ..\.venv\Scripts\python.exe -B -m app.modules.diet.migration_005 --database $temporaryDatabase --apply
```

不带 `--apply` 只读检查登记状态。正式库部署需另行授权、离线备份和恢复演练，本次开发未执行。

## 数据与归属

- `diet_weekly_plans`：开始日、份数、显式餐次目标比例、用户选定的共享目标、当前修订和上下文摘要。
- `diet_plan_items`：稳定的 21 个餐次 ID、日期/餐别、生成时食谱/食材/营养/来源快照以及上下文版本。
- `diet_plan_versions`：每次保存、刷新和反馈后的不可变计划版本快照。
- `diet_plan_feedback`：每个餐次当前状态、备注、原因、修订、操作者。
- `diet_plan_feedback_history`：每次显式反馈修改的追加历史，保存当时的计划修订及餐次生成修订，数据库触发器阻止改写/删除。
- `diet_plan_context_confirmations`：档案自由文本与用户明确选中的实际饮食规则的确认关系；保留确认人的真实账号 ID 和时间，不宣称完成食物过敏安全审核。

现有团队系统仍是本机共享 `profile_id=1` 单档案。admin/viewer 是这个共享档案的访问角色，**不是多租户健康数据隔离**。读取复用健康数据授权；掩码 viewer 不得通过饮食接口绕过隐私设置。写入要求 admin 和健康数据授权。账号 ID 只用于权限和操作审计，不伪造为不同个人档案。

## 推荐与档案变化

单餐推荐支持早餐、午餐、晚餐、加餐及不限餐次；公共食谱沿用原始数据包的餐次分类，私人食谱按用户设置的同名分类匹配。周计划为每个早/午/晚餐分别筛选，不再复用跨餐次候选缓存。未分类或自定义的非餐次分类保留为“餐次未标注”候选，不推断用途；已标注其他餐次的食谱不替代当前餐次。原公共库只有 1 道早餐、4 道午餐、3 道晚餐和 4 道加餐，唯一早餐被禁忌排除时会保留空早餐，不把加餐伪装为早餐。分类改名会使已保存计划提示更新，历史反馈保持不变。

每周连续 7 天，每天早/午/晚。推荐器先过滤明确命中的禁忌，再按既有分数排序；周计划优先减少连续和本周重复，不改评分公式。自 2026-10-29 起，未填写、未核验或过期的成分资料不单独排除食谱，仍显示未核验提示，不把未知解释为不含过敏原。具体食物/同源食品、精确食材名称及人工别名、已登记 contains/may_contain 关系仍参与禁忌匹配。没有候选就保留空餐次和原因，食谱不足明确标记重复。

营养目标只读取原饮食目标服务中生效的明确数值。餐次目标比例默认空，由用户选择后才参与目标比较；不会默认分配 30%/40%/30%。通用健康目标标题和单位没有可靠的营养语义，只保存用户选择的背景依据，不能转换为热量建议。

页面进入、重新可见、重新获得焦点及生成前检查上下文。指纹覆盖饮食相关过敏/偏好文本、有效结构化规则、每日营养目标、库存、食谱版本和公共目录内容版本；显示名称、档案更新时间本身等无关字段不触发刷新。服务端再次检查指纹，防止过期预览写入。

非空过敏文字必须由用户明确映射到实际有效 allergy/forbidden 规则；非空偏好必须映射到 like/dislike 规则。不能自动猜测，不能用“忽略”按钮跳过。文字或规则变化后重新确认；确认只证明用户的对应选择，不证明食物成分、加工配料或交叉接触安全。

新预览可自动重算。已保存计划只在用户查看刷新预览并确认后更新，**历史日期或曾有任何反馈的事项永不自动替换**，即使反馈后来改回 pending。失效的未来建议显示不可继续使用；历史快照和反馈保留。每次反馈也推进计划修订，使已展示的旧刷新预览失效，避免并发操作改变用户确认的范围。

已保存计划的日期、份数、餐次比例和所选共享目标固定。若选定的共享目标被删除，应创建新计划并重新选择目标；旧计划仍可查询，不覆盖它的历史。

## 反馈与统计

| 状态 | 界面 | 统计含义 |
| --- | --- | --- |
| pending | 灰色＋未反馈文字/图标 | 不等于失败 |
| completed | 绿色＋已完成 | 完成分子 |
| not_completed | 红色＋未完成 | 已反馈分母 |
| partial | 橙色＋部分完成 | 单独统计，不按 50% 折算 |
| not_applicable | 灰色＋不适用 | 不进入完成率分母 |

完成率 = completed / (completed + not_completed + partial)，分母为零显示暂无统计。反馈进度 = 非 pending 的有效餐次 / 已安排食谱的餐次。无候选餐次不进入成功/失败分母，只能保留 pending 或设为 not_applicable。未反馈天数为仍有 pending 的有效安排日期数，另外记录整日完全未反馈数。

反馈有独立 revision，过期写入返回 409，不覆盖后来反馈。反馈仅说明计划执行情况，既不自动新增实际饮食记录，也不扣减库存。

## API

所有路径位于 `/api/diet`，使用真实 Bearer 账号和健康数据授权。

| 方法与路径 | 功能 |
| --- | --- |
| GET `/weekly-plan-context` | 当前相关档案、规则、显式目标和指纹 |
| POST `/weekly-plan-context/confirm` | 明确确认自由文本映射（admin） |
| POST `/weekly-plans/preview` | 只读生成 21 餐预览 |
| POST `/weekly-plans` | 校验指纹、重新生成并保存可信快照（admin） |
| GET `/weekly-plans` | 分页查询计划 |
| GET `/weekly-plans/{id}` | 计划、有效性和当前统计 |
| POST `/weekly-plans/{id}/refresh-preview` | 查看未来未反馈项目刷新预览 |
| POST `/weekly-plans/{id}/refresh` | 确认刷新，要求上下文及计划 revision 一致（admin） |
| GET `/weekly-plans/{id}/versions` | 只读计划历史版本 |
| PUT `/weekly-plan-items/{id}/feedback` | 带反馈 revision 的状态更新（admin） |
| GET `/weekly-plan-items/{id}/feedback-history` | 反馈修改历史 |

客户端不能提交计算后的营养值、外部档案 ID 或伪造快照。服务端在同一 SQLite 事务快照中读取上下文和候选，写入事务失败回滚。

## 两个 PR 的边界

公共目录应先独立审核和合入 main；周计划随后基于已合入的公共目录提交第二个 PR。当前周计划工作树从最新 main 创建，并显式叠加尚未提交的公共目录依赖用于开发验证；这不表示公共目录已经在 main 中。本轮没有暂存、提交、推送或创建 PR。

公共目录 PR 包括只读数据库、006、公共/私人资源兼容、相应前端和回归测试。周计划 PR 只包括 005、上述周计划服务/接口、页面组件和测试文档。提交前按独立差异清单确认，不将依赖重复包装成周计划功能。
